# 设计：想法 → spec → 任务清单

先分类，再走路径。两条路径拿不准时，选更重的那条。任务中途发现的复杂度只升不降——停下说明，往上走。

## 第一步：探索

动手分类之前先看：文件、文档、最近的提交。要在既有代码上改东西，先读那个流程的现状。

## 三条路径

- **Spike（试探）**：可行性问题（"能不能……""糙点快点就行"）。2-3 句呈现问题和探针 → 点头 → 以正确性允许的最廉价方式调查 → 汇报建议。**产出是答案不是代码**；搭出来的东西全部标注一次性。想保留代码 = 新请求，重新分类。
- **Bounded（有界）**：对仓库中**已有**流程的边界清晰改动（新开关、小端点、单文件修复）。一次一个澄清问题 → 对话中呈现简短设计（方案 / 动哪些文件 / 怎么测）→ **停下等明确的"是"** → 用 executing 的单任务模式干。
- **Architectural（架构级）**：新项目、新子系统、改他人依赖的接口。走完本技能余下全部流程。

有界衡量的是**仓库**（要改的流程是否已存在、可读），不是任务大小，也不是你对这类应用的熟悉度。

请求描述了多个独立子系统（"带聊天、存储、计费、分析的平台"）？立刻指出，先分解成子项目，逐个走流程。

## spec（1 页）

- **目标**：一句话
- **架构决定**：2-3 句（组件怎么拆、数据怎么流）
- **全局约束**：精确值逐字写下（版本下限、依赖限制、命名/文案规则、平台要求）——后续每个 brief 逐字复制这一节
- **验收标准**：可判定（能写成"给这个输入 → 应得这个输出"）；解析/格式/边界类至少给 1-2 个具体输入→输出示例

**自审四查**（写完立刻跑，问题内联修掉）：
1. 占位符——有没有 TBD / "待定" / 含糊的需求？
2. 一致性——各节有没有互相矛盾？
3. 范围——单一任务清单装得下吗？装不下先分解
4. 歧义——哪条需求能读出两种意思？选定一种写死

## 任务清单（1 页，有序）

- 每任务一行：`交付物 + 验收要点`
- 同形小任务（同类单文件小改 ×N）合并成一行
- 顺序即执行序（全程串行）

## 呈现与移交

一条消息呈现三样东西：**spec + 任务清单 + 执行默认**，结尾一句：

> "批准即按此执行。执行默认：worktree 隔离、每任务提交、合并时 squash——要改默认现在说。"

- 任务清单**不等批准**——它随 spec 展示，用户可当场否决任何一行；不否决就按它执行
- 用户要求修改 → 改完重跑自审四查 → 重新呈现
- 用户批准 → **立即移交 executing，不再停留**
- Bounded 路径的批准同样硬：呈现设计，停住，等明确的"是"。呈现设计和开工在同一口气里 = 跳过了门

## 反合理化

| 借口 | 事实 |
|---|---|
| "太简单，不用出 spec" | 简单 = 更短的设计。Bounded 的两句话设计也是门。 |
| "细节执行时再定" | 歧义进 brief 就是返工源。现在定死。 |
| "大概齐了，先开工" | 自审四查没跑 = 没写完。 |
| "变更不大，算 bounded" | 有界看仓库有没有现成流程可改，不看大小。没有 = 架构级。 |
| "探针代码跑通了，留着吧" | Spike 产出是答案。保留代码是新请求，重新分类。 |
