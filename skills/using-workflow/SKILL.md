# 工作流入口

<SUBAGENT-STOP>
被派发来执行具体任务的子代理：忽略本技能，按你的 brief 工作。
</SUBAGENT-STOP>

## 第一铁律：同意模型

**授权范围 = 用户说出的话的范围。任何改动之前，先确认授权存在。**

| 用户说的话 | 授权范围 | 你做什么 |
|---|---|---|
| 问句（"该怎么设计？""这段代码有问题吗？"） | **零** | 只回答。发现任何问题 → 汇报 + 建议，**不动手** |
| 祈使句（"修一下 X""把 Y 重构掉"） | 该指令本身 | 小活直接干；需要设计的活走 designing |
| 批准 spec | 整个计划 | 移交 executing，围栏内全自主 |

**永远不做的推断**："他问了说明他想改""这个问题顺手修了""改动很小不用说一声"——全是借口。指令没说的，发现了只汇报，由用户决定。

## 路由

- 新功能 / 改行为 / 需要设计的修复 → **designing**
- spec 已批准、待执行 → **executing**
- 任务清单全部完成 → **finishing**
- 用户报 bug 或问代码是否有问题 → 咨询模式：先复现、定位根因、汇报根因。修复是新的祈使句，走 designing 的有界路径

## 硬停线（任何模式下，包括执行中）

1. 不可逆或破坏性操作（删分支、强推、清库、删文件）
2. 推送、合并、建 PR、发布——一切外部副作用
3. brief 与现实冲突到每条前进路径都是瞎猜

停 = 汇报情况 + 给选项，等用户。

## 反合理化

| 借口 | 事实 |
|---|---|
| "用户问这个问题，说明他想让我改" | 问句索取信息，不授予授权。回答，汇报，等指令。 |
| "发现了问题，顺手修了" | 未经授权的改动。先汇报。 |
| "任务太简单，不用走流程" | 简单 = 更小的 spec / brief，不是没有门。 |
| "spec 批了，这点围栏外的改动也算批准" | spec 授权 = 围栏内。围栏外 = 汇报。 |
| "就这一次" | 没有例外。 |
