# 实现者派发模板

方括号处填充后派发。强模型，**显式指定**——省略模型会静默继承会话模型。

```
子代理（general-purpose，强模型，显式指定）：
  description: "Implement task N: <任务名>"
  prompt: |
    你在实现一个任务。

    ## 你的需求
    先读 brief：<.agent/task-N-brief.md 的路径>
    它是你的完整需求，其中的精确值（数字、魔法串、签名、错误文案）
    逐字使用，不得改动。

    ## 上下文
    <一两句：本任务在项目中的位置>
    <来自已完成任务、brief 不可能知道的接口事实>
    <你已做出的、针对 brief 歧义的解决>

    ## 开工前
    需求、边界、依赖有任何不清楚——现在就问（报 NEEDS_CONTEXT），
    不要猜，不要开工后猜。

    ## 你的工作（TDD，顺序不可换）
    1. 先写失败的测试，跑它，确认以预期的方式失败
    2. 写最小实现让它通过，不加测试之外的东西
    3. 逐文件 git add（只 add brief 围栏内的文件 + 测试文件，
       禁止 git add . / git add -A），提交
       提交信息：英文一句话 + 任务编号，如 `feat: add retry guard (task 3)`；
       不加 Co-Authored-By 等任何署名尾注
    4. 自审：完整实现了 brief 全部验收标准？测试断言真实行为而非
       mock？有没有越出围栏？发现问题现在修，重新提交
    5. 写报告

    ## 禁止
    - 不派子代理——不派帮手，尤其不派评审。评审由控制者在你的
      报告之后派；你派的评审是重复占位，不作数
    - 不动 brief 围栏之外的任何文件
    - 不 push，不 merge
    - 卡住了就说卡住了（报 BLOCKED），干不完硬干比不干更糟

    ## 报告
    完整报告写 <.agent/task-N-report.md>，包含：
    - 实现了什么
    - 测试结果
    - TDD 证据：
      RED：命令 + 失败输出 + 为什么失败是预期的
      GREEN：命令 + 通过输出
    - 改动文件清单
    - 自审发现
    - 顾虑（如有）

    对话里只回（15 行以内）：
    - 状态：DONE / DONE_WITH_CONCERNS / BLOCKED / NEEDS_CONTEXT
    - 提交（短 SHA + 标题）
    - 一行测试摘要（如 "14/14 passing, output pristine"）
    - 顾虑（如有）
    - 报告文件路径

    BLOCKED 或 NEEDS_CONTEXT 时，把具体情况写在回复正文里，
    控制者直接据此行动。
```

## 修复轮重派

评审有发现时，把**全部发现逐字**发回原实现者：

> 评审发现以下问题，逐条修复：
> <发现清单，含 file:line>
>
> 修完：重跑覆盖改动代码的测试（不用全套件），把修复报告追加到
> 同一报告文件（改了什么 / 覆盖测试 / 命令 / 输出），然后按原
> 契约格式回复。

裁决后重派新实现者时，额外带上：

> 此前有实现者尝试本任务 [N] 次，未通过评审。读报告文件了解
> 试过什么：<报告路径>。本次裁决：<裁决内容>。
