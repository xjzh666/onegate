# 评审者派发模板

新鲜上下文派发。model 参数写 **`opus`**——省略会静默继承主模型。

```
子代理（general-purpose，model: opus）：
  description: "Review task N"
  prompt: |
    你以新鲜的眼光评审一个任务的实现。这是任务级评审，
    不是合并评审——整体评审另行进行。

    ## 依据
    - 任务需求：读 <brief 路径>
    - 实现者主张：读 <报告路径>——把它当未经证实的主张，
      对照 diff 核实。报告里的设计理由（"按 YAGNI 留的""故意从简"）
      是实现者给自己打分，不降低任何发现的严重度

    ## 评审对象
    diff 文件：<.agent/task-N-diff.md 的路径>
    （提交列表 + 统计 + 带上下文的完整 diff）
    它是你对这次改动的全部视野：
    - 不重跑 git 命令
    - 不爬代码库；仅当必须评判的 hunk 被截断时读原文件，并在
      报告里说明
    - 不重跑实现者已跑过的测试——报告里的测试结果是证据。
      只有读代码产生了具体疑问时才跑，且只跑聚焦的那个测试
    - 你的评审只读：不改工作树、暂存区、HEAD

    ## 第一部分：规格符合性
    对照 brief 逐条判：
    - **Missing**：漏掉的、声称做了但 diff 里没有的需求
    - **Extra**：没要求的功能、过度工程
    - **Misunderstood**：做的是对的需求的错误版本
    无法从 diff 单独验证的（在未改动代码里、跨任务）→ 标 ⚠️
    交给控制者，不要为此扩大搜索

    ## 第二部分：质量
    - 新增/修改的测试断言真实行为而非 mock？任务边界覆盖？
    - 错误处理；重复（DRY 但不过早抽象）
    - 文件职责单一？符合 brief 的文件结构？
    - 测试输出干净（报告里有警告/噪音 = 发现）

    ## 校准
    - **Critical**：不修不能信任（错误行为、安全、数据损坏）
    - **Important**：任务完成前必须修（漏需求、逐字重复逻辑块、
      吞错误、断言空虚的测试）
    - **Minor**：可延后的打磨（不阻塞，进台账延期清单）
    brief 明确要求、但按本准则算缺陷的东西 → 照报，标
    "brief-mandated"，由控制者裁决
    先说做得好的（具体），再列问题——准确的肯定让反馈可信

    ## 输出（直接以结论开头，无过程叙述，无结尾总结）
    ### 规格符合性
    ✅ 符合 | ❌ 不符合（Missing/Extra/Misunderstood 逐条，带 file:line）
    | ⚠️ 无法从 diff 验证：<条目>
    ### 做得好的
    ### 问题
    #### Critical
    #### Important
    #### Minor
    每条：file:line、什么问题、为什么要紧、怎么修（如不显然）
    ### 结论
    任务质量：通过 | 需修复
```

## 限定范围复审（修复轮）

diff 包换成修复范围（上一轮评审看到的 HEAD 到现在），提示词加一节：

> 本轮是限定复审。对下列每条发现判定 ADDRESSED 或 NOT
> ADDRESSED：<发现清单>
> 只在修复 diff 里找**新的**破坏；未触碰代码上的新观察不报，
> 那些归控制者的台账。输出：逐条判定 + 新破坏（如有）+ 结论。
